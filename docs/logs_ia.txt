S000.1 - Estrutura de Camadas Spring Boot
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica de separação de responsabilidades entre Controller, Service e
Repository em uma API REST Spring Boot? Me dê um exemplo conceitual de fluxo.

[RESPOSTA]
A separação segue o princípio de responsabilidade única:

1. Controller: recebe requisições HTTP, valida entrada, delega ao Service e
   retorna resposta. Não contém lógica de negócio.
   Exemplo conceitual:
   @RestController
   @RequestMapping("/produtos")
   public class ProdutoController {
       private final ProdutoService service;
       // construtor
       @PostMapping
       public ResponseEntity<ProdutoResponse> criar(@RequestBody @Valid ProdutoRequest req) {
           ProdutoResponse resp = service.criar(req);
           return ResponseEntity.status(HttpStatus.CREATED).body(resp);
       }
   }

2. Service: contém regras de negócio, orquestra repositórios, aplica
   transações.
   Exemplo conceitual:
   @Service
   @Transactional
   public class ProdutoService {
       public ProdutoResponse criar(ProdutoRequest req) {
           validarNomeUnico(req.nome());
           Produto entidade = mapper.toEntity(req);
           return mapper.toResponse(repositorio.save(entidade));
       }
   }

3. Repository: abstrai acesso ao banco (Spring Data JPA).
   Exemplo conceitual:
   public interface ProdutoRepository extends JpaRepository<Produto, Long> {
       boolean existsByNome(String nome);
   }

Lógica: Controller → Service → Repository → Banco. Retorno inverso.

[DECISAO]
Estrutura de camadas adotada e aplicada manualmente em todos os módulos.

S000.2 - DTOs vs Entidades JPA
--------------------------------------------------------------------------------
[PROMPT]
Por que não expor diretamente a entidade JPA no endpoint? Qual a lógica por
trás do uso de DTOs? Me dê um exemplo.

[RESPOSTA]
Expor entidade JPA causa:
- Vazamento de estrutura interna (acoplamento)
- Exposição acidental de campos sensíveis (senha, tokens)
- Dificuldade de versionar contratos
- Problemas com lazy loading (LazyInitializationException)

Lógica do DTO: camada de contrato externa, imutável, validada.
Exemplo conceitual (Java 17+ record):
public record ProdutoRequest(
    @NotBlank String nome,
    @NotNull @DecimalMin("0.01") BigDecimal preco
) {}

public record ProdutoResponse(Long id, String nome, BigDecimal preco) {}

Mapeamento manual no Service:
Produto entidade = new Produto(req.nome(), req.preco(), unidade);
ProdutoResponse resp = new ProdutoResponse(entidade.getId(), entidade.getNome(), entidade.getPreco());

[DECISAO]
Uso de DTOs próprios para entrada e saída, sem exposição direta das entidades.
Records foram empregados em estruturas imutáveis específicas; os demais DTOs
utilizam classes Java. O mapeamento permanece explícito na aplicação.

S000.3 - Validação com Bean Validation
--------------------------------------------------------------------------------
[PROMPT]
Como validar entrada de dados em endpoints REST? Qual a lógica do @Valid e
como capturar erros de forma padronizada?

[RESPOSTA]
Lógica: anotações JSR-380 no DTO + @Valid no parâmetro do controller.

Exemplo conceitual no DTO:
public record PedidoRequest(
    @NotNull Long clienteId,
    @NotNull @Size(min = 1) List<ItemPedidoRequest> itens,
    @Pattern(regexp = "BALCAO|DELIVERY|MESA") String canal
) {}

No controller:
@PostMapping
public ResponseEntity<?> criar(@RequestBody @Valid PedidoRequest req) { ... }

Quando a validação falha, o Spring lança MethodArgumentNotValidException.
A lógica de captura é centralizada em @RestControllerAdvice:
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handle(MethodArgumentNotValidException ex) {
    List<String> detalhes = ex.getBindingResult().getFieldErrors().stream()
        .map(e -> e.getField() + ": " + e.getDefaultMessage())
        .toList();
    return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY)
        .body(new ErrorResponse("VALIDACAO_FALHOU", "Dados inválidos", detalhes));
}

[DECISAO]
Validação declarativa com Bean Validation e handler global de erros 422.

S000.4 - JPA: Relações e Lazy vs Eager
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica de escolha entre FetchType.LAZY e EAGER no JPA? Como evitar
N+1 queries ao listar pedidos com itens?

[RESPOSTA]
Lógica:
- LAZY (padrão para @OneToMany/@ManyToMany): carrega sob demanda. Evita
  carregar dados desnecessários, mas exige transação aberta ao acessar.
- EAGER (padrão para @ManyToOne/@OneToOne): carrega junto. Risco de carregar
  árvore inteira desnecessariamente.

Regra prática: quase sempre LAZY. Carregamento explícito quando necessário.

Para evitar N+1, usar JPQL com JOIN FETCH:
@Query("SELECT p FROM Pedido p JOIN FETCH p.itens i JOIN FETCH i.produto " +
       "WHERE p.unidade.id = :unidadeId")
List<Pedido> listarComItens(@Param("unidadeId") Long unidadeId);

Ou EntityGraph:
@EntityGraph(attributePaths = {"itens", "itens.produto"})
@Query("SELECT p FROM Pedido p WHERE p.unidade.id = :unidadeId")
List<Pedido> listarComItens(@Param("unidadeId") Long unidadeId);

[DECISAO]
FetchType.LAZY em todas as coleções. JOIN FETCH ou EntityGraph para casos
de leitura específica.

S000.5 - Transações e @Transactional
--------------------------------------------------------------------------------
[PROMPT]
Quando e como usar @Transactional? Qual a lógica de propagação e rollback?

[RESPOSTA]
Lógica: @Transactional demarca unidade de trabalho. Commit no fim do método
se não houver exceção; rollback automático em RuntimeException.

Exemplo conceitual:
@Service
public class PedidoService {
    @Transactional
    public PedidoResponse criar(PedidoRequest req) {
        validarEstoque(req.itens());         // leitura
        Pedido pedido = montarPedido(req);   // escrita
        debitarEstoque(req.itens());         // escrita
        return mapper.toResponse(repo.save(pedido));
    }
}

Propagações comuns:
- REQUIRED (padrão): participa da transação existente ou cria nova.
- REQUIRES_NEW: sempre cria nova transação (útil para logs de auditoria).
- SUPPORTS: usa a existente se houver, senão executa sem transação.

Rollback seletivo:
@Transactional(noRollbackFor = RegraNegocioLeveException.class)

Cuidado: @Transactional não funciona em chamadas internas da mesma classe
(proxy do Spring).

[DECISAO]
@Transactional apenas em métodos de Service que envolvem escrita ou múltiplas
leituras consistentes.

S000.6 - Autenticação JWT: Conceito e Fluxo
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica do fluxo JWT em uma API stateless? Por que stateless?

[RESPOSTA]
Lógica stateless: o servidor NÃO guarda sessão. Cada request carrega sua
própria prova de identidade (o token).

Fluxo:
1. Cliente envia credenciais → POST /auth/login
2. Servidor valida e emite JWT assinado (HS256 ou RS256) contendo:
   - sub (identificador do usuário)
   - roles (CLIENTE, FUNCIONARIO, ADMIN)
   - exp (expiração)
3. Cliente armazena token e envia em cada request via header:
   Authorization: Bearer <token>
4. Filtro intercepta, valida assinatura e expiração, popula SecurityContext.

Vantagens stateless:
- Escalabilidade horizontal (sem sessão em memória)
- Simplicidade para mobile/SPA
- Facilita microserviços

Desvantagens:
- Não há revogação imediata (solução: blacklist curta ou tokens de curta
  duração + refresh token)

Exemplo conceitual de filtro:
public class JwtFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) {
        String header = req.getHeader("Authorization");
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);
            Claims claims = jwtService.validar(token);
            Authentication auth = jwtService.toAuthentication(claims);
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        chain.doFilter(req, res);
    }
}

[DECISAO]
JWT stateless com claims customizados (roles + unidadeIds). Filtro próprio
populando SecurityContext.

S000.7 - Spring Security: Cadeia de Filtros
--------------------------------------------------------------------------------
[PROMPT]
Como funciona a cadeia de filtros do Spring Security 6? Qual a lógica de
configurar autorizações por rota?

[RESPOSTA]
Lógica: SecurityFilterChain é uma lista ordenada de filtros. Cada request
passa por todos até ser aceito, rejeitado ou redirecionado.

Exemplo conceitual de configuração:
@Bean
public SecurityFilterChain chain(HttpSecurity http) throws Exception {
    return http
        .csrf(AbstractHttpConfigurer::disable)           // API stateless
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/auth/**", "/swagger-ui/**", "/v3/api-docs/**").permitAll()
            .requestMatchers(HttpMethod.GET, "/produtos/**").hasAnyRole("CLIENTE", "FUNCIONARIO", "ADMIN")
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated()
        )
        .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
        .exceptionHandling(ex -> ex
            .authenticationEntryPoint(entryPoint401)
            .accessDeniedHandler(handler403)
        )
        .build();
}

Regras de precedência:
- Primeira regra que casa é a aplicada (ordem importa).
- requestMatchers com path variable no meio: usar * (não **).
- hasRole("ADMIN") verifica autoridade "ROLE_ADMIN".

[DECISAO]
SecurityFilterChain stateless, CSRF desabilitado, JWT filter antes do
UsernamePasswordAuthenticationFilter.

S000.8 - REST: Verbos HTTP e Códigos de Status
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica de escolha entre POST, GET, PUT, PATCH e DELETE? E os códigos
200, 201, 204, 400, 401, 403, 404, 409, 422, 500?

[RESPOSTA]
Verbos (semântica):
- GET: leitura idempotente.
- POST: criação de recurso.
- PUT: substituição completa (idempotente).
- PATCH: atualização parcial (idempotente).
- DELETE: remoção (idempotente).

Status (lógica):
- 200 OK: sucesso com corpo.
- 201 Created: recurso criado (retornar Location).
- 204 No Content: sucesso sem corpo (ex: DELETE).
- 400 Bad Request: payload malformado.
- 401 Unauthorized: não autenticado.
- 403 Forbidden: autenticado mas sem permissão.
- 404 Not Found: recurso inexistente.
- 409 Conflict: conflito de estado (ex: duplicidade, idempotência).
- 422 Unprocessable Entity: payload válido sintaticamente, mas semanticamente
  inválido (erros de validação de negócio/DTO).
- 500 Internal Server Error: falha não tratada.

Idempotência: GET, PUT, DELETE podem ser repetidos sem efeito colateral
adicional. POST e PATCH (na prática) também, mas a semântica formal é mais
fraca para PATCH.

[DECISAO]
Convenção REST aplicada: PATCH para status, 422 para validação, 409 para
conflitos de negócio.

S000.9 - Tratamento de Exceções Centralizado
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica de um handler global de exceções? Por que centralizar?

[RESPOSTA]
Lógica: um único ponto transforma exceções em respostas HTTP padronizadas.
Evita duplicação, garante contrato uniforme.

Exemplo conceitual:
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(RecursoNaoEncontradoException.class)
    public ResponseEntity<ErrorResponse> handle404(RecursoNaoEncontradoException ex,
                                                   HttpServletRequest req) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorResponse(ex.getCodigo(), ex.getMessage(),
                                    List.of(), Instant.now(), req.getRequestURI()));
    }

    @ExceptionHandler(RegraNegocioException.class)
    public ResponseEntity<ErrorResponse> handle409(RegraNegocioException ex,
                                                   HttpServletRequest req) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(new ErrorResponse(ex.getCodigo(), ex.getMessage(),
                                    List.of(), Instant.now(), req.getRequestURI()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handle422(MethodArgumentNotValidException ex,
                                                   HttpServletRequest req) {
        List<String> detalhes = ex.getBindingResult().getFieldErrors().stream()
            .map(e -> e.getField() + ": " + e.getDefaultMessage()).toList();
        return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY)
            .body(new ErrorResponse("VALIDACAO_FALHOU", "Dados inválidos",
                                    detalhes, Instant.now(), req.getRequestURI()));
    }
}

Vantagens:
- Contrato uniforme (RNF de padronização).
- Facilita testes (asserts em schema fixo).
- Frontend consome erros de forma previsível.

[DECISAO]
@RestControllerAdvice com ErrorResponse imutável e handlers por tipo de
exceção.

S000.10 - Testes Unitários com Mockito
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica de isolar o Service em teste unitário usando Mockito?

[RESPOSTA]
Lógica: mockar dependências (Repository, outros Services) para testar apenas
a lógica do Service sob teste.

Exemplo conceitual:
@ExtendWith(MockitoExtension.class)
class PedidoServiceTest {

    @Mock private PedidoRepository repository;
    @Mock private EstoqueService estoqueService;
    @InjectMocks private PedidoService service;

    @Test
    void deveCriarPedidoQuandoEstoqueSuficiente() {
        // given
        PedidoRequest req = umPedidoValido();
        doNothing().when(estoqueService).validarDisponibilidade(req.itens());
        when(repository.save(any())).thenAnswer(inv -> inv.getArgument(0));

        // when
        PedidoResponse resp = service.criar(req);

        // then
        assertThat(resp.id()).isNotNull();
        verify(estoqueService).validarDisponibilidade(req.itens());
        verify(repository).save(any(Pedido.class));
    }

    @Test
    void deveLancarExcecaoQuandoEstoqueInsuficiente() {
        PedidoRequest req = umPedidoValido();
        doThrow(new RegraNegocioException("ESTOQUE_INSUFICIENTE"))
            .when(estoqueService).validarDisponibilidade(req.itens());

        assertThatThrownBy(() -> service.criar(req))
            .isInstanceOf(RegraNegocioException.class)
            .hasMessageContaining("ESTOQUE_INSUFICIENTE");
    }
}

Padrão AAA: Arrange (given), Act (when), Assert (then).

[DECISAO]
Testes unitários de Service com Mockito, cobrindo caminhos felizes e de
exceção.

S000.11 - Testes de Integração com @SpringBootTest
--------------------------------------------------------------------------------
[PROMPT]
Qual a diferença entre teste unitário e de integração? Como testar o
controller com MockMvc?

[RESPOSTA]
Diferença:
- Unitário: uma classe isolada, dependências mockadas. Rápido.
- Integração: várias camadas reais (ou quase). Mais lento, mais realista.

Exemplo conceitual com MockMvc:
@SpringBootTest
@AutoConfigureMockMvc
class PedidoControllerIntegrationTest {

    @Autowired private MockMvc mockMvc;
    @Autowired private ObjectMapper mapper;

    @Test
    void deveRetornar422QuandoItensVazios() throws Exception {
        PedidoRequest req = new PedidoRequest(1L, List.of(), "BALCAO");

        mockMvc.perform(post("/pedidos")
                .contentType(MediaType.APPLICATION_JSON)
                .content(mapper.writeValueAsString(req))
                .with(tokenCliente()))
            .andExpect(status().isUnprocessableEntity())
            .andExpect(jsonPath("$.error").value("VALIDACAO_FALHOU"))
            .andExpect(jsonPath("$.details").isArray());
    }
}

Vantagem: testa roteamento, validação, serialização e segurança juntos.

[DECISAO]
Combinação de testes unitários para serviços e autorização com testes de
integração voltados ao contexto Spring, às migrações, à persistência, à
concorrência e à geração do contrato OpenAPI. O contrato HTTP também é
exercitado pela coleção Postman.

S000.12 - Padrões de URL e Versionamento
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica de design de URLs REST? Como versionar a API?

[RESPOSTA]
Lógica de URLs:
- Substantivos no plural, minúsculos, separados por hífen: /pedidos-itens.
- Hierarquia clara: /unidades/{id}/produtos.
- Query params para filtros: /produtos?unidadeId=5&nome=tapioca.
- Evitar verbos na URL: usar verbo HTTP, não /produtos/buscar.

Versionamento (opções):
1. URL: /v1/pedidos (explícito, simples).
2. Header customizado: Accept: application/vnd.raizes.v1+json.
3. Parâmetro: ?version=1 (menos recomendado).

Recomendação para projetos acadêmicos/pequenos: versionar por URL (/v1).

[DECISAO]
URLs RESTful com substantivos plurais. Versionamento por URL quando houver
breaking change.

S000.14 - Soft Delete vs Hard Delete
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica de escolher entre soft delete e hard delete? Como implementar
soft delete no JPA?

[RESPOSTA]
Lógica:
- Hard delete: remove fisicamente. Simples, mas perde histórico e quebra
  integridade referencial.
- Soft delete: marca como inativo. Preserva histórico, auditoria e
  referências.

Implementação JPA:
@Entity
@Table(name = "produto")
@SQLRestriction("ativo = true")   // Hibernate 6+
public class Produto {
    @Column(nullable = false)
    private boolean ativo = true;

    public void inativar() { this.ativo = false; }
}

Endpoint:
@DeleteMapping("/{id}")
public ResponseEntity<Void> inativar(@PathVariable Long id) {
    service.inativar(id);
    return ResponseEntity.noContent().build();
}

Vantagens:
- Histórico preservado (pedidos antigos continuam legíveis).
- Possibilidade de "restaurar".
- Conformidade com auditoria.

[DECISAO]
Exclusão lógica por indicadores de atividade e consultas específicas nos
serviços e repositórios. A solução final não utiliza @SQLRestriction.

S000.15 - Idempotência em Operações Críticas
--------------------------------------------------------------------------------
[PROMPT]
Como garantir que um pagamento não seja processado duas vezes se o cliente
clicar duas vezes?

[RESPOSTA]
Lógica: verificar estado antes de processar (idempotência de negócio).

Exemplo conceitual:
@Service
public class PagamentoService {
    @Transactional
    public PagamentoResponse processar(Long pedidoId, PagamentoRequest req) {
        Pedido pedido = pedidoRepo.findById(pedidoId)
            .orElseThrow(() -> new RecursoNaoEncontradoException("PEDIDO_NAO_ENCONTRADO"));

        // Idempotência: se já existe pagamento aprovado, retorna o existente.
        pagamentoRepo.findByPedidoAndStatus(pedido, StatusPagamento.APROVADO)
            .ifExists(p -> throw new RegraNegocioException("PAGAMENTO_JA_PROCESSADO"));

        Pagamento pagamento = gatewayMock.chamar(pedido, req);
        pagamentoRepo.save(pagamento);
        return mapper.toResponse(pagamento);
    }
}

Alternativa avançada: header Idempotency-Key (RFC draft), com tabela de
chaves já processadas.

[DECISAO]
No pagamento, a repetição é protegida pela verificação do estado e pelo
bloqueio pessimista do pedido. Na criação do pedido, a aplicação também aceita
Idempotency-Key e rejeita a reutilização da chave com conteúdo diferente.

S000.16 - CORS e Segurança de Frontend
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica do CORS e quando configurá-lo?

[RESPOSTA]
Lógica: navegador bloqueia requests cross-origin por padrão. O servidor
precisa autorizar explicitamente via headers.

Exemplo conceitual:
@Bean
public CorsConfigurationSource corsSource() {
    CorsConfiguration cfg = new CorsConfiguration();
    cfg.setAllowedOrigins(List.of("http://localhost:5173")); // Vite/SolidJS
    cfg.setAllowedMethods(List.of("GET", "POST", "PATCH", "DELETE", "OPTIONS"));
    cfg.setAllowedHeaders(List.of("*"));
    cfg.setAllowCredentials(true);
    cfg.setExposedHeaders(List.of("Authorization", "Location"));

    UrlBasedCorsConfigurationSource src = new UrlBasedCorsConfigurationSource();
    src.registerCorsConfiguration("/**", cfg);
    return src;
}

@Bean
public SecurityFilterChain chain(HttpSecurity http) throws Exception {
    return http.cors(Customizer.withDefaults()) /* ... */ .build();
}

Regras:
- Em produção: restringir origens (nunca "*").
- Expor apenas headers necessários.
- allowCredentials=true exige origem específica (não "*").

[DECISAO]
CORS configurado com origens específicas por perfil (dev/prod).

S000.17 - Migrations com Flyway
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica de usar migrations versionadas (Flyway) em vez de deixar o
Hibernate criar o schema?

[RESPOSTA]
Lógica: migrations garantem:
- Schema reproduzível em qualquer ambiente.
- Evolução controlada (histórico de mudanças).
- Compatível com CI/CD e múltiplos desenvolvedores.
- Dados iniciais (seed) versionados.

Estrutura típica:
src/main/resources/db/migration/
  V1__criar_tabelas_basicas.sql
  V2__adicionar_unidades.sql
  V3__criar_pedidos.sql
  V4__ajustes_lgpd.sql

Regras Flyway:
- Nome: V<numero>__<descricao>.sql
- Nunca alterar migration já aplicada (criar nova).
- Para consolidar em ambiente limpo: squash em V1 único (apenas antes do
  primeiro deploy em produção).

Exemplo conceitual:
-- V1__schema_completo.sql
CREATE TABLE usuario (
    id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    nome VARCHAR(120) NOT NULL,
    email VARCHAR(160) NOT NULL UNIQUE,
    senha_hash VARCHAR(255) NOT NULL,
    ativo BOOLEAN NOT NULL DEFAULT TRUE,
    criado_em TIMESTAMP NOT NULL DEFAULT NOW()
);

[DECISAO]
Flyway com migrations versionadas. Schema consolidado em V1 para
reinstalação limpa.

S000.18 - Perfis de Aplicação (dev/test/prod)

[PROMPT]
Como organizar configurações por ambiente no Spring Boot?

spring.datasource.url=jdbc:postgresql://${DB_HOST}:5432/raizes

Regra: NUNCA colocar credenciais reais no repositório. Usar variáveis de
ambiente (${DB_PASSWORD}).

[DECISAO]
Três perfis (dev, test, prod) com segredos via variáveis de ambiente.

S000.19 - Logs e Auditoria
--------------------------------------------------------------------------------
[PROMPT]
Qual a lógica de logging estruturado e como auditar operações sensíveis?

[RESPOSTA]
Lógica de logging:
- Usar SLF4J + Logback.
- Níveis: ERROR (falhas), WARN (anomalias), INFO (eventos de negócio),
  DEBUG (detalhes técnicos).
- Nunca logar dados sensíveis (senha, token, CPF completo).

Exemplo conceitual:
@Slf4j
@Service
public class PagamentoService {
    public PagamentoResponse processar(Long pedidoId, PagamentoRequest req) {
        log.info("Processando pagamento - pedidoId={}", pedidoId);
        // ...
        log.info("Pagamento aprovado - pedidoId={}, pagamentoId={}", pedidoId, pag.getId());
        return mapper.toResponse(pag);
    }
}

Auditoria de operações sensíveis (cancelamento, estorno):
@Entity
@Table(name = "auditoria_cancelamento")
public class AuditoriaCancelamento {
    @Id private Long id;
    private Long pedidoId;
    private Long usuarioId;
    private String motivo;
    private BigDecimal valorEstornado;
    private Instant realizadoEm;
}

Regra: auditoria em tabela separada, imutável, apenas insert.

[DECISAO]
Logs SLF4J com correlação e pseudonimização, complementados pelos históricos
persistidos em pedidos, pagamentos, cupons, consentimentos e movimentações de
estoque. Não foi criada uma tabela exclusiva de auditoria de cancelamentos.
